# Автономна робота та підключення Firebase

SADOK працює за принципом local-first: локальна SQLite-база та налаштування доступні без мережі, а Firebase використовується лише для передачі журналу змін і подальшої синхронізації між робочими місцями.

## Що вже підготовлено

- PWA-пакет кешує інтерфейс, SQLite WebAssembly та початкову базу.
- SQLite зберігається в IndexedDB.
- важливі записи `localStorage` дублюються в окремій IndexedDB;
- браузер запитує стійке сховище, щоб зменшити ризик автоматичного очищення;
- щоденні локальні резервні копії проходять `PRAGMA integrity_check`;
- Firebase SDK завантажується лише після ввімкнення хмарного режиму;
- Firestore Rules забороняють доступ користувачам, які не є активними членами закладу.

## Поточний хмарний проєкт

- Firebase project ID: `sadok-kzdo-145`;
- тариф: Spark без підключеного платіжного акаунта;
- Firestore: Standard, регіон `eur3`, захист від видалення ввімкнений;
- Firebase Authentication: Email/Password увімкнено;
- Google Analytics: вимкнено;
- Firestore Rules та індекси опубліковано;
- Web App `SADOK Web` зареєстровано;
- Firebase-конфігурацію додано до Vercel для Production, Preview і Development;
- production-домен `eda-ashen.vercel.app` додано до дозволених доменів Authentication.
- первинного адміністратора створено та додано до `organizations/kzdo-145/members` з роллю `admin`;
- вхід через Firebase Auth і запис журналу через Firestore Rules перевірено приймальним тестом.
- адміністратор може створювати постійні облікові записи співробітників у формі «Налаштування → Доступ і контроль → Ролі», призначати роль, вимикати вхід і надсилати лист для зміни пароля;
- продукти, страви, компоненти технологічних карт і харчові профілі мають стабільні sync ID та версії;
- меню, затвердження меню, постачальники, прибуткові накладні та складські партії також синхронізуються між пристроями;
- локальні CRUD-зміни накопичуються окремо від журналу й автоматично передаються після повернення мережі;
- первинні копії каталогів, меню та складу завантажуються до `organizations/kzdo-145/entities`, а наступні пристрої отримують їх з хмари;
- одночасне редагування на різних пристроях не перезаписується мовчки: конфлікт показується для ручного вибору локальної або хмарної версії.
- ролі обмежують хмарні зміни: медсестра працює з меню й техкартами, комірник — зі складом і накладними, кухар — із меню та техкартами, керівник і адміністратор — з усіма цими даними.

## Підключення окремого закладу

1. Створити Firebase-проєкт і Firestore у production mode.
2. Увімкнути Email/Password у Firebase Authentication.
3. Скопіювати `.env.example` у `.env.local` та заповнити публічну Web App конфігурацію.
4. Вказати стабільний `VITE_FIREBASE_ORGANIZATION_ID`, наприклад `kzdo-145`.
5. Виконати `npx firebase-tools login`, потім `npx firebase-tools use <project-id>`.
6. Опублікувати правила: `npx firebase-tools deploy --only firestore:rules,firestore:indexes`.
7. У Firestore створити `organizations/<organization-id>` та документи членів у `members/<auth-uid>` з полями `active: true`, `role: "admin" | "director" | "nurse" | "warehouse" | "cook"`.
8. Додати ті самі `VITE_FIREBASE_*` змінні до Vercel та повторити production deployment.

Не зберігати service-account JSON, приватні ключі або серверні токени у Vite-змінних: усе з префіксом `VITE_` доступне браузеру.

## Обов'язковий приймальний тест

1. Встановити SADOK через кнопку в налаштуваннях.
2. Відкрити основні розділи, щоб сформувався локальний стан.
3. Вимкнути Wi-Fi та повністю закрити браузер.
4. Запустити встановлений SADOK, створити тестову зміну і резервну копію.
5. Увімкнути Wi-Fi та перевірити відправлення локальної черги.

Перед передачею дитячому садку також зберегти контрольну резервну копію на зовнішній носій.
